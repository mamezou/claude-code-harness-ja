# 送付ドラフトの作成

対象は Teams (先方向け) と Slack (内部向け) のチャット文面。
設計書・見積書クラスの長文資料は対象外 (ドキュメント作成ガイドに従う)。
型の出典は `archive/sent/` の送付済み実例と
`.claude/rules/external-deliverables.md`。
案件ごとに、置き場を各案件の drafts ディレクトリに読み替える (型は共通)。

ひな形の `<差出人>` は利用側で自分の名乗り (所属 + 氏名) に置き換える。

## 作成前に固定する

- 用途: 返信 / 依頼 / 相談 / 報告 / 共有案内 / 内部の軽い連絡 のどれか
- 宛先とチャネル (先方 = Teams、内部 = Slack)。宛先は指示にある人だけ。
  指示にない宛先・cc を足さない
- 文面に使う根拠を「確認済み事実」と「推測・未確認」に分けて応答内に示す。
  文面に使えるのは確認済み事実のみ。ドラフトファイルには送信本文だけを書き、
  内部メモ・メタ情報は入れない
- 本文を書く前に、文面の設計 5 点を 5 行以内で依頼者へ示し、OK を得る:
  1. 宛先と通数 (実施依頼と判断相談は 1 通に混ぜない)
  2. 依頼か相談かの別
  3. 実施の分担 (先方作業と当方作業)
  4. 添付の形 (何を渡すか)
  5. 期待する返事 (実施の連絡か、可否の判断か)

## 指摘を受けたときの対応

- 指摘を「文言」か「設計 (宛先・通数・分担・構成・添付)」かに分類する
- 文言の指摘は最小差分で直す
- 設計の指摘は、該当の設計 5 点を直したうえで全文を作り直す。局所の張り替えを
  しない (張り替えは別の矛盾を生む)。作り直したら、受けた指摘の一覧と
  突き合わせてから出す

## 置き場と命名

- `<案件>/docs/drafts/<チャネル>-<宛先>-<件名>-YYYYMMDD-draft.txt`
- 拡張子は .txt、中身は送信本文のみ
- 送付が確認できたら即 `archive/sent/` へ移動する (移動は送付確認後の別作業)

## 用途別の型とひな形

Teams の依頼・返信は `templates/` のひな形の複製から作る。
構成を新規に作文しない。

- 依頼: `templates/teams-request.txt`。用件・現状 1〜2 文 → 「■ 項目名」+
  「・ラベル: 値」の一覧 → 返してほしい物と送る物 → 締め
- 相談 (可否の判断を求める): `templates/teams-consult.txt`。相談の 1 文 →
  現状と理由 → 変更後も残る安全の仕組み → 了承時の作業 (添付・元・変更) →
  難しい場合の道
- 返信 (質問への回答): `templates/teams-reply.txt`。「＞ 質問文」で引用 → 直後に
  「結論: 〜」 → 理由。質問が複数ならこの組を繰り返す
- 共有案内: `templates/share.txt`。共有物の名前と場所 → 資料名+1行説明 →
  見てほしい点 → 依頼 (確認・返答)
- 報告 (実施の連絡): `templates/report.txt`。結論 1 文 → 実施内容 → 確認結果 →
  次の作業。依頼・お伺いを混ぜない
- 内部の軽い連絡 (訂正・お礼・FYI): `templates/slack-note.txt`。1〜2 文の単発
- 依頼者宛のチャット報告は Output Style「Concise JA」「成果物報告の型」に従う
  (send-draft の対象外)
- 行数・箇条書きは実例からの目安で、情報量に応じて短くする側に倒す

依頼ひな形の記入規則:

- 項目行は「ラベル: 値」のみ。理由・注意・説明の文を入れない。理由は設計資料側に
  置き、必要なら参照 1 文で案内する
- 期限・催促を書かない。書くのは依頼者が期限を指定した場合のみ
- 「別途」「準備でき次第」等の後送を書く前に、今渡せないかを確認する。渡せる物は
  添付・記載で今回の依頼に含める
- 質問・依頼に入れてよいのは、先方にしか答えられない・先方にしかできない事項のみ
- 値・設定指示の各行は出典 (実環境コマンド・実装コード・設計書) を応答内の根拠区分に
  示す。設計書のみが出典の値は、実装・実環境との照合まで行う

## チャネル別の型

Teams (先方向け):

- 宛名「〇〇 様」。cc があれば下の行に「cc 〇〇 さん」
- 挨拶「お世話になっております。<差出人>です。」、締め「よろしくお願いいたします。」
- 感嘆符は使わない。長文の区切りは「■」見出し (Markdown の # は使わない)
- コードブロックは使わず、ファイル名・値は地の文か箇条書きに書く

Slack (内部向け):

- 宛名・挨拶・締めは書かない。必要なときだけ先頭にメンション
- 本文から直接始める

## 長さの目安

- 質問 1 点への回答: 1000 バイト未満
- 依頼・一覧を含む文面: 1500〜2500 バイト
- 迷ったら短い側に倒す。相手が既に知っていることを説明しない

## 構成と通し読み

- 構成の順序: 経緯 (2〜3 文) → 依頼 → 当方で実施する事項 → 締め。経緯を末尾に置かない
- Sid・ARN・設定差分などの詳細は本文に並べず、添付ファイルへ置く。本文は変更の
  趣旨と理由に絞る
- 長い英字の識別子は初出のみフル表記し、以後は呼び名で書く (同一識別子 3 回以上は
  hook が差し戻す)
- 書き終えたら、送付相手の目で頭から通し読みする。機械チェックの通過を品質確認と
  しない。通し読みの判定は draft-precheck の必須項目として応答に書く

## 送付前チェック (必須)

Write 後に draft-precheck Skill を対象ファイルへ実行する。hook
(`draft-precheck.sh`) は `*-draft.txt` も対象だが、
検査するのは編集差分の禁止語・内部表現のみで、指示語の件別判定は
draft-precheck Skill にしかない。省略しない。ヒットゼロと指示語の判定を
確認してから依頼者へ提示する。送付は依頼者が行う。

あわせて Codex CLI のレビューを挟む。観点は
「受信者が一読で内容と依頼を理解できるか (順序・矛盾・専門語の密度・依頼の明確さ)」。
コマンドの型は codex-review Skill を使い、
指摘は 1 件ずつ採否を示す。外部送付物に Codex への言及を書かない。

## 指摘を受けた 2 回目以降

- 直す範囲は指摘された箇所に限る。形 (文章 / 箇条書き) と分量は、指示がない限り変えない。
  指摘への反動で逆へ振らない
- 依頼が入れる内容を決めていない (「調整して」「作って」で項目の指定がない) ときは、
  推測で選ばず、書く前に入れる項目・入れない項目・形・分量を 1 回で確認する。
  新規・調整とも同じ。機械検知はなく、判断で防ぐ
- 修正版も毎回 draft-precheck を通す (1 文 60 字の検知を含む)。Slack 文面も対象
